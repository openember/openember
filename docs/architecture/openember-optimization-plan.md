## 目标与边界

从 Mock 闭环走向可接入真实硬件、可恢复、可验证的产品运行框架。保留 Node / Link、Hardware Interface 和现有系统节点分工，不重做通信层，不增加新的 HAL 大层次。

本文统一管理优化顺序和验收进度；具体接口与行为仍以 [Hardware Interface](../design/hardware-interface.md)、[硬件实施计划](../design/hardware-interface-implementation-plan.md) 和 [Runtime Supervision](runtime-supervision-and-product-app-design.md) 为准。发生调整时同步这些文档，不维护相互矛盾的接口定义。

相比借鉴分析中的初始顺序，本计划将回归基线提前，并在 OTA 之前用真实硬件验证接口。设备选型未确定不阻塞 Mock、安全边界和部署恢复工作。

## 关键约束

- 连续控制目标可以采用最新值缓存；离散安全操作必须单独定义顺序、确认和恢复条件，不能被普通目标覆盖。
- 命令失联使用接收端单调时钟；发送端时间不直接参与跨设备超时判断。源节点名称不等于可信身份。
- 单写者不仅是进程内互斥，还需要设备权限和部署所有权。维护模式也不能旁路安全校验。
- 安全输出由产品及执行器决定；双足保持与轮式停车不同。析构无法覆盖进程崩溃，硬件 / MCU watchdog 需单独验收。
- health_monitor 汇总事实，Product App 决定产品行为，本地执行器保护不等待远端健康汇总。
- OS 与 launch_manager 不同时直接监督同一子进程。恢复入口不能全部位于待更新 release 内。
- OTA 的原子切换和断电持久性分别验证；应用目录方案不能代替系统镜像及 MCU 固件的更新设计。
- 暂不建设通用插件系统、多控制源仲裁框架或产品行为树框架。

## 阶段 1 执行记录

已使用现有 CTest、MinUnit、示例程序及 Python 标准库实现，不增加测试框架依赖。

- 独立配置入口：`cmake/RegressionDefaults.cmake`，构建目录 `build-regression/`，不修改产品 `.config` 和 `build/`。
- 单元基线：算法、日志、OSAL、actuator 及 MinUnit 示例。
- 硬件进程基线：配置拒绝、IMU / Temperature / GNSS 消息、Joint 命令执行及失联安全输出、服务停止与重新启动。
- 监督进程基线：失败重启及上限、正常退出不重启、启动心跳超时、运行中被终止后重启、监督器正常退出清理子进程。
- 运行命令、前置条件、日志位置与验证记录见 [测试说明](../unit-test.md)。

基线建设发现 Hardware Interface 原先未处理 SIGTERM，进程会直接被信号终止。本阶段补充最小的 SIGINT / SIGTERM 协作退出：处理器只记录标志，主线程退出 Spin 后执行 Stop 和 Shutdown。完整的控制线程 / 回调生命周期优化仍属于阶段 2。

2026-09-16 验证：独立配置和全量构建通过；CTest 7/7 通过；两组进程测试各连续运行三次通过。下一步进入阶段 2，优先处理本地命令接收时间、单写者执行以及停止期间的回调生命周期。

阶段 1 的宿主机进程测试不代表阶段 4 的 OS 部署恢复完成，也不代表真实硬件、断电恢复或硬实时能力已验证。配置错误测试也不等同于完整配置解析器覆盖。
